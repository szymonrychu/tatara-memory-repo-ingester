# MEMORY.md - tatara-memory-repo-ingester

- 2026-07-29 (fix/code-graph-bulk-batching): #31 - `/code-graph:bulk` is now pushed as bounded batches instead of one whole-repo request. VERIFIED FIRST, both sides: `run.go:222` shipped the entire aggregated graph in one POST, and tatara-memory's `internal/codegraph/pgstore.go` `Reconcile` wraps a whole push in ONE `BeginTx`..`Commit` executing row-at-a-time, with its own handler comment stating a large-repo reconcile "legitimately runs 50-194s" - so the transaction boundary IS per request (the one cross-repo assumption issue #31's pre-mortem demanded validating) and client batching really does shorten it. That long transaction holding a shared-pool connection is the client-side root of tatara-memory#82/#79/#80/#87 (bulk 5xx pool starvation). SIZING measured, not guessed: a full ingest of this repo is 939 rows / 291 KB over 137 files (~310 B/row), so `MaxBatchRows=2000` is ~620 KB and ~2000 statements per transaction (sub-second), and `MaxBatchFiles=250` bounds the other half of the work (reconcile issues 4-5 DELETEs per file before any insert, so a deletion/rename-heavy push is capped even with almost no rows). The server's 32 MiB body cap is NOT the binding constraint - transaction duration is. Both caps keep a small repo's full ingest and the common incremental push as a SINGLE request (pre-mortem 2: batching must not multiply per-transaction overhead on small repos). BATCH BOUNDARY = whole files (pre-mortem 1): reconcile deletes are `WHERE repo=$1 AND src_file/file_path=$2 AND extractor=$3`, so a file split across two batches would have batch 2's purge delete what batch 1 inserted; a single file whose rows exceed the cap therefore ships alone in an oversized batch. Cross-batch edges are SAFE: `code_edges` has no FK to `code_entities` (no FKs at all in the codegraph schema), so an edge may reference an entity another batch inserts, in either order. Entities with an EMPTY `file_path` are legal server-side (repo/package-scoped, e.g. `go_package`) so unfiled rows ride in the FIRST batch exactly once - and any row whose file is genuinely not in `Files` also rides there so the server still rejects it loudly (400) instead of it being silently dropped client-side. SEQUENTIAL on purpose: bounded concurrency would put back the pool pressure this removes. PARTIAL FAILURE is explicit, not silent: batches commit independently, so a failure at batch k leaves 1..k-1 committed; PushGraph aborts immediately and returns an error naming batch k/N, the repo, and the files already committed, the run fails, the operator leaves `LastIngestedCommit` unchanged, and the replayed `--since` window converges (every batch is an idempotent upsert + per-file reconcile). BACKOFF: `doWithRetry` now honours `Retry-After` (delay-seconds AND HTTP-date, capped 60s) on 429 and backs off exponentially (200ms doubling, capped 10s, maxRetries 2->4) otherwise, so the client works against today's 503 shedding AND the 429+Retry-After admission control tatara-memory is adding (fix/bulk-admission-control) without depending on it landing. New metrics: `code_graph_batches_total{result}`, `code_graph_batch_rows`, `push_retries_total{path,reason}`, `push_shed_responses_total{path,status}`; `push.Client.WithMetrics` carries the run registry into the push package (nil registry = no-op, so tests need no wiring). OUT OF SCOPE (tracked in ROADMAP): mirroring the `/memories:bulk` async 202+job pathway for the graph endpoint (option 1b/3b), which needs a coordinated tatara-memory change.

- 2026-06-28 (tatara/fix-19-quarantine-a-hard-failing-analyzer-group): #19 - completed the fail-closed design (#16) into fail-ISOLATED. A hard `Analyze()` error (whole-batch failure: `go/packages` load fault, recovered tree-sitter panic, ctx cancel) used to set `incomplete` and abort the whole run before any push (old `run.go:179-181`), so one poison file wedged ingestion for the WHOLE repo forever (operator never advances `LastIngestedCommit`, retries the same window at 30m backoff). NOW `run.go` quarantines just the failing analyzer's group (`fs == groups[a.Name()]`) into a new `quarantined` set AND into the existing `failedFiles`, then `continue`s; the run completes and exits zero so the operator advances HEAD and every healthy group + future commit keeps flowing. CRUX (the one place quarantine differs from soft `failedFiles`): the graph push reconciles over `Files` and `failedFiles` does NOT filter it, so quarantined files MUST also be removed from the graph `Files` set (`graphFiles = touched - quarantined`), else the server's reconcile-by-Files purges their last-good entities with no replacement (the destructive partial #16 guards against). Chunk reconcile already excludes `failedFiles` (now incl. quarantined). DELETIONS stay correct: deleted/renamed-old paths are never in any analyzer group, never quarantined, stay in `graphFiles` + reconcile so their stale rows purge. When EVERY touched file is quarantined (no deletions) `graphFiles` is empty -> skip the graph push (server 400s on empty `Files`) but still return nil. RESIDUAL STALENESS (accepted, bounded): a quarantined file re-analyzes only when it (or, for `go/packages`, any file in its package) re-enters the `--since` diff; a package-wide fault fixed by a sibling commit that does not touch the poison file leaves that file stale until its OWN next edit. Reported via new counter `ingest_files_quarantined_total` - label is `language` (= analyzer name), NOT `{analyzer}` as the issue wrote, for consistency/correlation with the other `analyzer_*` series (operator#68 alerting) + WARN log with analyzer/paths/error. Test seam `options.newRegistry` (mirrors existing `options.getenv`) injects a `hardFailAnalyzer` because a real `packages.Load` top-level fault is hard to trigger reproducibly; a pre-cancelled ctx only proves the no-wedge property (all groups fail at once). NOTE: this agent container has NO gcc, so the cgo packages (`cmd/tatara-ingest`, `internal/analyze`) could not be built/tested locally - only `internal/obs` (pure Go) was verified here; CI (build-essential present) is the gate. OUT of scope: per-file bisection within a group, any operator-side change.

- 2026-06-23 (fix/terraform-module-scoped-ids): INCIDENT - the `terraform` (GitLab) repo ingest failed 47x with `/memories:bulk` 400 "duplicate idempotency key in batch". ROOT CAUSE: the terraform analyzer alone emitted name-only entity IDs (`tf:variable:<name>`, `tf:resource:<type>.<name>`) AND constant chunk bodies, so same-named blocks in different ROOT MODULES (e.g. `variable "projects"` in `gitlab/` and `harbor/`) produced byte-identical idempotency keys; the whole repo ships as ONE bulk batch and tatara-memory rejects in-batch dup keys with a permanent (non-retryable) 400. Every other analyzer already qualifies IDs by their natural scope (Go=pkgPath, helm=chartName, docs=file path); terraform was the only one path-blind. FIX: scope entity IDs AND edge targets by `moduleDir = filepath.Dir(relPath)` - DIR not file, because HCL refs resolve within a root module (directory), so intra-module cross-file edges (output in outputs.tf -> var in variables.tf) still resolve; edge targets in `edgesFromExpr`/`dependsOnEdges` compute the same `moduleDir(srcFile)` so they align with the dir-scoped entity IDs. Also carry `relPath` in chunk Body so identical cross-module blocks don't get content-deduped by LightRAG into one memory (silent loss). Backstop: last-wins dedup by idempotency key in `push.ItemsFromChunks` (keyed on the full key, NOT an ordinal - preserves cross-run idempotency). SECOND latent bug fixed by the same change: name-only IDs also clobbered the code graph (`code_entities` PK is `(repo,id)`, upsert ON CONFLICT DO UPDATE - same-named cross-module entities silently overwrote each other). Server-side option (memory tolerates dup keys via internal PK) was REJECTED for this incident: alone it converts the loud 400 into silent memory loss; the client emitting colliding keys was the real defect. Deploy = bump INGESTER_IMAGE tag in tatara-helmfile.

2026-08-23 (tatara-memory#111, companion) **The hyperedge arity filter counted the wrong thing: `len(h.Nodes)` on the model's PRE-remap node ids, while the ids it actually emits are remapped and can collapse.** `remapID` resolves through a table built as `remap[n.ID] = conceptID(repo, n.Label)`, and `conceptID` is `concept:<repo>:<slugLabel(label)>` - keyed on the slugified LABEL, not on the node id and not on the node type. So three routes collapse distinct nodes to one member id, all reachable: two node ids carrying the same Label (the extraction spec's id format is `{parent_dir}_{filename}_{entity}`, so one concept named in two files is two ids and one label); two labels that slugify identically ("Token Validation" / "token-validation"); and a literal duplicate id in `nodes`. Nothing upstream prevents any of them - `internal/llm/openai.go` asks for `{"type":"json_object"}`, plain JSON mode with no schema, so there is no `uniqueItems` and no validation, and extraction_spec.txt is self-CONTRADICTORY here: it specifies the stem-based id format and then says ids "must be deterministic from the label alone", and BOTH readings produce the collapse. Separately the member loop never dropped empty ids, unlike the edge loop above it which drops empty endpoints - so `nodes:["a","b",""]` emitted a member naming nothing.

Why it became urgent: `codegraph.Push` in tatara-memory now rejects a hyperedge with fewer than 3 DISTINCT members, and an empty member id. `internal/push/push.go` returns on the first failing batch with no retry and 400 is not transient, so ONE collapsed hyperedge discards that batch and every batch after it - including the `FileSHAs` cache upsert riding along at the end of the semantic push, so the same files stay misses and the same failure recurs next run. Best-effort (`cmd/tatara-ingest/run.go` logs and returns without failing the run) means it degrades silently rather than loudly: a WARN with the same `err` label a network blip produces.

Fix: remap, drop empty, dedup preserving FIRST-SEEN ORDER, then apply `< 3` to the deduped slice, and pass that same slice to both `hyperedgeID(...)` and `Members`. Order preservation is load-bearing - `hyperedgeID`'s fallback branch hashes the members, so a map iteration would make ids non-deterministic. Deduping before the id is computed keeps the id and the stored members agreeing. Nothing is stored anywhere yet (the memory stack is Disabled on all three projects), so changing ids costs nothing today. **Do not "simplify" the arity check back to `len(h.Nodes)`** - the comment on it says why.

Known and NOT fixed here: `hyperedgeID` returns `he:<repo>:<slugfile>:<slugmodelid>`, so two hyperedges in one file whose model ids slugify identically collide; tatara-memory upserts on `(repo, id)` while members insert `ON CONFLICT DO NOTHING`, so the second one's members UNION with the first's instead of replacing them. Not a 400 - a quiet wrong answer, and its own issue.
